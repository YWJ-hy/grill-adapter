# migrate-wiki › Obsidian Note Maintenance

This reference defines mode 7: a post-migration, proposal-driven audit and repartition of active
bound Obsidian atomic Notes. It reuses the normal Obsidian binding, write bridge, candidate
journal, publisher, and verify contracts. It never edits a Vault worktree directly.

## Atomicity decision

Treat one Note as one execution-time retrieval unit. Propose a sibling Note when a candidate
inside the existing Note has a different:

- trigger or implementation phase;
- lifecycle or ownership boundary;
- failure mode or validation matrix;
- task-routing need;
- update/archive cadence.

Keep tightly coupled normative rules, anti-patterns, and their examples together. A shared
component name, directory, or code owner is not sufficient reason to keep unrelated contracts
in one Note.

## Batch proposal

Use a bounded batch and show a table like:

```text
Source: iho-expense-shared
Scope: frontend/cnhis-design-vue-guidelines

Existing Note: .../iho-table-wrapper
  keep/update: initialization-sensitive-config
  create: low-code-field-normalization
  reason: different lifecycle, input contract, and failure mode
  edges: preserve inbound links; add see-also only when useful
```

For every split, preserve the old `wiki_id` for the retained contract. New IDs must be stable,
semantic, unique within the bound Sources, and reflected consistently in Note frontmatter, paths,
typed links, journal receipts, and the publish allowlist.

## Confirmation gates

Defer the batch when any of these cannot be resolved from bounded reads:

- the old Note's retained responsibility;
- the new Note's owner or target Source;
- a `depends_on` versus `see_also` edge;
- an inbound backlink that would become stale;
- path/ID collision, binding drift, neutrality violation, or write policy refusal.

Do not infer semantic duplicate or ownership decisions from token overlap or filenames. Ask the
user to choose when sibling Notes versus a topic directory changes long-term taxonomy.

## Recovery

Keep the maintenance plan, feature journal, write receipts, and publish run manifest locally.
On interruption, rerun the same proposal/apply or publish step after resolving the reported
external issue. Never delete the manifests, accept a drifted hash as a new baseline, or reopen
cut-over legacy roots.
