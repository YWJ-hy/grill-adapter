# setup-init-obsidian

Use this skill when a user asks to initialize, connect, migrate, or repair
Obsidian for a project's governed Wiki runtime. This is the complete setup
orchestration entry point. It must use the two published npm packages from this
repository:

- `grill-adapter` for project wiring and project doctor;
- `@grill-adapter/obsidian-wiki` for machine-local Obsidian configuration,
  health, and bridge operations.

Reuse those package CLIs and the `migrate-wiki` skill; do not duplicate their
configuration, migration, or write logic with repository scripts or direct MCP
bundle invocations. Continue through migration apply, publication, verify, and
cutover when the user supplies the required confirmations and external merge
results; do not stop merely because a plan was generated.

The skill is resumable: whenever an external action or an explicit user decision
is required, report the exact blocker and stop. When the user returns with the
result, re-run the relevant check and continue from the first incomplete phase.
Never guess a Vault, Source, repository, bridge token, remote legacy URL, or
migration decision.

## Safety boundaries

- Do not modify legacy Markdown, indexes, graphs, Obsidian Notes, Source
  manifests, or the machine registry as part of setup.
- Do not start a write bridge with guessed roots, projects, ports, or tokens.
  Once the user has explicitly asked for complete setup and the package config
  declares all values, start it as a managed background process through the
  npm CLI (`obsidian-wiki bridge start`) and verify it with
  `obsidian-wiki bridge status`; do not leave the foreground bridge command
  blocking the setup session.
- Do not use a legacy Wiki as a runtime fallback when Obsidian is active.
- Do not invoke a migration apply, verify, or cutover without the separate
  confirmations required by `migrate-wiki`.
- Preserve unrelated project settings when creating or completing
  `.grill-adapter/settings.json`; never store Vault filesystem paths, bridge
  tokens, credentials, or machine-local registry data in the project.

## Phase 1: inspect and normalize the project

1. Resolve the project root (`git rev-parse --show-toplevel`, falling back to
   the current directory only when it is already a project directory).
2. Read `.grill-adapter/settings.json` if it exists. Record:
   - `wiki.provider`
   - `wiki.obsidian.bindings`
   - `wiki.legacyRuntime`
   - whether a project Source binding exists and is readable.
3. Detect legacy roots without reading their contents:
   `.grill-adapter/wiki/`, `.shared-adapter/wiki/`, and (for older projects)
   `.adapter/wiki/`. Also detect an old `.adapter/` settings directory when
   `.grill-adapter/` is absent.
4. If an old `.adapter/` directory is the only adapter directory, do not merge
   it blindly. Tell the user which directory would be renamed and ask for
   confirmation; after confirmation, rename it to `.grill-adapter/` only when
   the destination does not exist, preserving all bytes. If both exist, stop
   and ask the user to resolve the overlap.

## Phase 2: verify and initialize the two npm packages

Check the user's global npm environment before running any setup command. npm
may return a non-zero status when a package is absent; still inspect its JSON
output and treat absence as a setup state, not as permission to use checkout
scripts:

```bash
npm list --global --depth=0 --json
```

The result must contain both `grill-adapter` and
`@grill-adapter/obsidian-wiki`, and both `grill-adapter` and `obsidian-wiki`
executables must resolve on `PATH`. When package metadata from this plugin is
available, reject an incompatible installed version and ask the user to update
both packages together. Do not substitute the checkout's
`manage.sh`, Python scripts, `node mcp/obsidian-wiki/dist/index.js`, or a
hand-written replacement when either package is absent.

If either package is missing, ask the user for authorization to install them.
After authorization, run this command in the session and recheck the result:

```bash
npm install --global grill-adapter @grill-adapter/obsidian-wiki
```

If npm reports a permission or registry error, report that exact error and wait;
do not switch to local source execution or ask the user to copy package files.

Prefer automation:

1. Run `obsidian-wiki init`. This is idempotent and must not overwrite an
   existing active config.
2. Run `obsidian-wiki config validate`.
3. Run `obsidian-wiki doctor`, then run:

   ```bash
   grill-adapter doctor <project-root>
   ```

   Treat either command's non-zero result as a setup blocker. Report the
   actionable error (missing Vault selector, repository worktree/remote,
   bridge configuration, credentials, or stale base) and wait for the user to
   fix that external state. Do not edit the machine config or start the bridge
   on their behalf unless they explicitly ask for that exact operation and all
   values are already declared in the config.

The two package CLIs are the only supported setup path. Do not claim that the
plugin's bundled MCP server or a checkout-local script replaces either package.

## Phase 3: wire the project to the installed plugin

Use the `grill-adapter` npm CLI for project wiring. Reuse an existing host
marker when present. If no host/runtime can be determined from `CLAUDE.md`,
`AGENTS.md`, or the current session, ask one compact question for the intended
host (`grill` or `plain`) and runtime (`claude`, `codex`, or `both`), then run:

```bash
grill-adapter install <project-root> --host <host> --runtime <runtime>
grill-adapter verify <project-root> --host <host> --runtime <runtime>
```

Do not copy skills into the project or patch a host skill. If wiring is already
valid, leave it unchanged.

## Phase 4: explain and complete Source/repository topology

If settings already contain valid Obsidian bindings, preserve them, summarize
the existing Wiki inventory, and ask whether the user wants to keep it as-is or
add another Wiki library. If settings are missing, the provider is not
`obsidian`, or no readable project binding exists, do not ask the user to invent internal IDs.
First explain the plain-language choices below, derive
stable identifier candidates from the answers, and ask the user to confirm or
edit those candidates.

Explain the topology before asking for values:

- `vaultRef` is a logical key into the machine-local `obsidian-wiki` config.
  The actual Vault filesystem directory and selector stay in that package
  config; they never belong in the project settings.
- `root` is a Vault-relative directory inside that Vault and is the Obsidian
  Wiki directory for this Source. It is not a project-relative path.
- `repositoryRef` is a logical key into the same machine-local config. It
  selects the Git worktree/remote/base branch that owns that Source root.
- A single GitHub repository is supported: multiple non-overlapping project or
  shared Source roots may point at the same `repositoryRef`.
- Multiple GitHub repositories are supported: give each Source binding its own
  `repositoryRef`; the migration publisher creates one draft PR per affected
  repository. A Source root cannot span repositories, and roots in one Vault
  cannot overlap or be nested.
- The machine-local config must contain a matching Vault entry and repository
  entry for every referenced `vaultRef`/`repositoryRef`; `obsidian-wiki doctor`
  is the authority for validating this topology.

### Required multi-Wiki inventory

Before collecting Vault or repository fields for a new or incomplete setup,
ask this explicit question in plain language:

```text
这个项目需要连接几个 Wiki 库？
请列出每个 Wiki 库的用途，例如“项目开发知识”“团队共享规范”“产品文档”。
系统允许每个项目最多一个 project Wiki，但可以有多个 shared Wiki；
不同 Wiki 可以位于不同 Vault、目录或 Git 仓库。
```

Treat each answer as a separate Source candidate. Do not silently merge
different purposes into one root, and do not silently turn several project
Wiki candidates into several `role: project` bindings. If the user wants more
than one project-specific library, explain the one-project-Source limit and
ask which one is the project Source; model the remaining portable libraries as
`role: shared` only after the user confirms that meaning.

When existing bindings are present, show the discovered Source names, roles,
Vault-relative roots, and repository references first, then ask:

```text
已发现这些 Wiki 库。要保留全部、保留并新增，还是只继续配置其中指定的库？
现有 binding 不会被删除；如需移除或换绑，请单独说明。
```

Preserve every existing binding unless the user explicitly authorizes a
replacement. For a new setup, a single-library answer is valid and creates
one confirmed Source; propose `role: project` only when its stated purpose is
project-specific. A multi-library answer creates one mapping row per confirmed
Source. Never infer a second Wiki from a repository name, a directory listing,
or an old legacy root.

### User-facing intake

For each confirmed Wiki library, ask in plain language before showing internal
field names:

- **What is this Wiki used for?** Repeat the user's purpose in the mapping and
  use it to distinguish project knowledge from portable shared knowledge.
- **Which Obsidian Vault should hold this Wiki?** Ask for the Vault's name as
  shown in Obsidian and, only when the local registry does not already know it,
  the local Vault folder. Explain that the Vault is the knowledge workspace,
  not the project repository.
- **Where inside that Vault should this Wiki's Notes live?** Ask for a
  Vault-relative folder such as `Projects/my-app` or `Shared/engineering`.
  Explain that this is the Wiki directory, not a path inside the code project.
  Propose a folder from the library purpose and project name and ask for
  confirmation.
- **Which Git repository stores that Wiki folder?** Ask for the local worktree
  folder, Git remote, and base branch. Explain that this repository receives
  governed draft PRs for Wiki changes. If all roots share one repository,
  propose one shared repository entry; otherwise propose one per repository.
- **Should this Wiki be project-only or shared with other projects?** Explain
  that `project` rules are local to this project and `shared` rules are
  portable across projects.
- **Should this Wiki be readable?** Explain that read access is needed for
  research and implementation context; write access remains separately
  governed. Default `read: true` only after the user confirms.
- **Should any legacy Wiki content migrate into this Wiki?** Explain that this
  selects a migration target only; migration still needs separate plan/apply/
  cutover authorization. Record the exact local legacy root or remote shared
  Wiki URL supplied by the user, and never infer a target when several Source
  candidates exist.
- **Should the local bridge be enabled?** Explain that it is the loopback
  writer used for governed Note changes. Propose the environment variable name
  `OBSIDIAN_WIKI_BRIDGE_TOKEN`; never ask the user to paste the token into
  chat or a config file.

Then show the derived mapping and ask for one confirmation:

```text
Human choice                         Derived configuration
Wiki "项目开发知识"                 purpose: project development
Vault "Engineering Knowledge"       vaultRef: engineering-knowledge
Folder "Projects/my-app"             root: Projects/my-app
Wiki worktree/remote                 repositoryRef: engineering-wiki
Project-only                         role: project
Readable for research                access.read: true
```

For multiple libraries, show one complete row per Wiki before asking for one
confirmation. Keep the purpose visible so the user can distinguish otherwise
similar paths:

```text
Wiki purpose | sourceId | role | vaultRef | repositoryRef | Vault-relative root | read?
项目开发知识 | app-project | project | engineering-knowledge | engineering-wiki | Projects/my-app | yes
团队共享规范 | team-shared | shared | engineering-knowledge | engineering-wiki | Shared/engineering | yes
```

The user provides facts and confirms the mapping in chat; they must not edit the
JSONC registry by hand. Only ask for an explicit internal ID when the proposed
candidate collides with an existing entry. For multiple repositories, show one
row per Wiki and call out the repository change; do not silently reuse a
repository when the user chose separate repositories. After the user confirms
the mapping:

1. Run `obsidian-wiki config path --json` to resolve the active machine config.
2. Upsert every Vault entry through the npm package, using JSON on stdin:

   ```bash
   printf '%s' '<vault-json>' | obsidian-wiki config upsert-vault
   ```

   Include `vaultRoot`, bridge `url` or `host`/`port`, `tokenEnv`,
   `allowedRoots`, and `projectDirs` when bridge operation is required.
3. Upsert every Git repository entry through the npm package:

   ```bash
   printf '%s' '<repository-json>' | obsidian-wiki config upsert-repository
   ```

4. If an existing entry differs, show the before/after identity and ask for
   authorization before repeating the same command with `--replace`. Never
   overwrite a machine entry silently.
5. Run `obsidian-wiki config validate` and both doctors again.

These commands create parent directories and write the machine config with
user-only permissions. Do not ask the user to open or edit the JSONC file.
Then create or update `.grill-adapter/settings.json` automatically, preserving
unrelated keys and using the documented conservative defaults:
`publishing.mode: git-pr`, `updateExistingPage: skip`, and
`createNewDocument: ask`. Ensure the binding uses a relative Vault root and
contains no `..`, absolute path, token, or credential.

Then rerun both package CLIs' doctors from Phase 2. If complete setup was
requested and the config declares bridge values, first check
`obsidian-wiki bridge status`; if it is unhealthy, start the foreground CLI as a
background process using the host's process manager, then recheck status and
rerun both doctors. On POSIX use `nohup obsidian-wiki bridge start > <log> 2>&1
&`; on Windows use `Start-Process` with the same npm executable. A healthy
active Obsidian provider is the `shadow-validation` state while legacy roots
remain; it is not cut over.

## Phase 5: route and finish legacy Wiki migration

If no legacy root was detected, report that setup is ready and stop.

If one or more legacy roots were detected:

1. Show the exact roots and state that setup will leave them byte-for-byte
   unchanged.
2. Ask explicitly whether the user authorizes the complete migration lifecycle,
   beginning with a **read-only migration plan**, via `migrate-wiki`. A refusal
   leaves the roots untouched and setup can still finish with Obsidian active.
3. For a local legacy project/shared root, invoke `migrate-wiki` in Obsidian
   **plan-only** mode after authorization.
4. For a remote legacy shared Wiki, ask the user for the exact source Git URL:

   ```text
   legacy shared-wiki Git URL (https or ssh, without embedded credentials):
   ```

   Pass it as `--legacy-shared-wiki-url <git-url>`. Never infer this URL from
   the project's `origin`, an Obsidian target `repositoryRef`, or a GitHub
   organization name. The planner clones it only into a disposable directory
   and pins the source commit. If the user has a local clone instead, ask them
   to place/copy it under `.shared-adapter/wiki/` or provide the URL; do not
   scan arbitrary directories.
5. Pass explicit Source selectors when more than one project or shared binding
   is available. Never guess among multiple bindings.
6. Present every plan issue and wait for the user's confirmation of this exact
   plan. Then invoke `migrate-wiki` apply with its required `--confirmed` gate.
   Do not hand-edit the plan or call the write bridge directly.
7. Report every draft PR and stop while the user reviews and merges them. After
   the user confirms all migration PRs are merged and the configured base
   worktrees are synchronized, invoke `migrate-wiki` verify.
8. Show the exact roots that will become read-only archives and ask for a
   separate cutover confirmation. Only after that confirmation invoke
   `migrate-wiki` cutover with its required confirmation gate.

The migration skill owns all plan issue confirmations (`semantic-split`,
`duplicate-id`, `dangling-edge`, `target-path-collision`, neutrality, pack, and
strength gates), CAS writes, publication, merge verification, and cutover
write-protection. Keep resuming this lifecycle after each user response; do not
claim complete setup until doctor reports `cutover-complete` when legacy roots
were migrated, or `shadow-validation`/healthy Obsidian when no migration was
authorized.

## Completion report

Report:

- project root and whether `.grill-adapter/settings.json` was created or
  preserved;
- host/runtime wiring result from `grill-adapter install/verify`;
- `obsidian-wiki` and project doctor results;
- configured Source bindings, Vault-relative roots, and affected
  `repositoryRef` values (never print machine-local paths or secrets);
- active adoption state (`shadow-validation` or `cutover-complete`);
- detected legacy roots and migration lifecycle state (plan, applied draft PRs,
  merged/base-synchronized, verified, or cut over);
- any exact external action still waiting on the user.

Never claim that migration or cutover is complete merely because setup or a
plan succeeded. Future knowledge reads use bound Obsidian Sources only; legacy
content is migration evidence until `migrate-wiki` completes its own verify and
separate cutover confirmation. The final success state is a healthy
`obsidian-wiki doctor`, a healthy `grill-adapter doctor`, valid project wiring,
and `cutover-complete` when legacy roots were migrated.
