# Capture Content Templates

This reference guides canonical atomic Note content inside a Capture Plan. A queued Note remains a
non-authoritative draft until draft-PR merge and synchronized-base verification.

## Atomic Note Contract

Every Note contains one independently materializable contract and begins with complete v1
frontmatter:

```markdown
---
wiki_schema: grill-adapter.obsidian-note/v1
wiki_id: <stable-source-scoped-id>
type: constraint|domain|decision|guide
status: active
agent_visible: true
summary: <one precise retrieval summary>
---

# <Precise title>

<durable content>
```

Use typed edges only when their exact target Note exists in formal base or the current project
overlay: `depends_on`, `see_also`, `supersedes`, or `contradicts`. Section fragments may be included
in link values, but the Note path before `#` must resolve.

## Contract Depth

For APIs, commands, schemas, infrastructure, or cross-layer behavior, include the applicable parts
of this structure rather than a vague summary:

1. scope and trigger;
2. signatures or identities;
3. invariants and lifecycle;
4. validation/error behavior;
5. good, boundary, and bad cases;
6. tests required;
7. wrong versus correct usage.

Keep distinct triggers, lifecycles, failure modes, validation paths, or task routing in sibling
Notes. Do not inflate one Note merely because contracts share a module or owner.

## Type Guidance

- `constraint`: executable hard/soft rules future implementation must obey.
- `domain`: stable business/domain facts, not implementation details.
- `decision`: a durable non-ADR choice with real alternatives and trade-offs.
- `guide`: a reusable checklist or Skill Card discovery Note.

## ADR Execution Projection

```markdown
---
wiki_schema: grill-adapter.obsidian-note/v1
wiki_id: <stable-project-id>
type: constraint
status: active
agent_visible: true
summary: <implementation scope constrained by the ADR>
constraint_strength: hard
adr_source_id: project-adr:<sha256>
adr_source_path: docs/adr/<file>.md
adr_source_content_hash: sha256:<canonical-content-hash>
---

# <ADR title> - execution constraints

> Derived projection. The project ADR is authoritative for context, options, rationale, status,
> and consequences. Edit the ADR, then regenerate this projection.

- <future executable obligation>
```

Do not copy ADR narrative. If no durable execution obligation remains, skip with the controlled
reason from `targeting.md`.

## Skill Card

A Skill Card is `type: guide` and must include the exact staged pack identity:

```yaml
skill_name: <kebab-case-name>
skill_version: <semver>
skill_contract_hash: sha256:<pack-hash>
skill_roles:
  - implementer
  - reviewer
skill_triggers:
  - <specific scenario>
```

The body explains when to invoke the pack; normative executable detail stays in the pack itself.

## Quality Checklist

- Start from skip and require final evidence.
- Make one explicit `create`/`update` decision with stable `wiki_id`/path and semantic reason.
- Preserve existing Note, ADR, and Skill Card identities on update.
- Create a sibling or defer when the candidate changes the target theme.
- Keep Shared content portable and free of blocked project identifiers.
- Resolve every typed edge against formal base or current-project overlay.
- Use precise summary/body language and include validation/tests for behavioral contracts.
- Never include secrets, tokens, transient task narration, candidate transcript, or agent reasoning.
