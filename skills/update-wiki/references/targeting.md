# Capture Targeting

This reference is private input to the isolated `wiki-capture` role. It governs semantic target
selection only. The staging interface independently validates binding, policy, schema, identity,
hash, typed-link, path, Git, and journal invariants.

## Evidence Gate

Start from `skip`. Queue only durable reusable contracts, domain facts, conventions, gotchas, or
hard-to-reverse surprising decisions supported by final evidence. Accepted review findings and
verified code/tests outrank final spec/tickets, which outrank candidate wording. Candidate prose
alone is never proof.

Use `defer` when evidence, ownership, contradiction, or target identity needs a user decision.
Do not ask inside the child and do not guess to avoid a deferred result.

## Formal And Draft Views

Formal catalog/search/read sees only merged, synchronized base. The Capture draft view adds only
the current project's ordered `queued`/`pr-open` overlay and is non-authoritative.

1. Read draft metadata without bodies.
2. Use catalog/search to narrow formal candidates by Source and path prefix.
3. Read only plausible formal or overlay targets within the supplied body limit.
4. Prefer the latest current-project overlay version when refining a queued path.

Never use another project's Outbox, scan an entire Vault, or treat queued/open-PR content as formal
knowledge.

### Obsidian Atomic Note Targeting

An atomic Note is one independently materializable durable contract.

- An accepted same-theme refinement updates the existing Note and preserves its stable `wiki_id`.
- A contract with a distinct trigger, lifecycle, failure mode, validation path, task route, Card
  identity, or ADR authority creates a sibling Note with a new stable `wiki_id`.
- Same module,
  directory, or code owner is not sufficient evidence that two contracts belong in one Note.
- Never change an existing Note's `wiki_id` to absorb a new topic.
- If bounded evidence cannot determine the boundary, record `defer` so the coordinator reports a
  needs-decision count.

For every queued decision, bind one exact Source, `create|update` operation, normalized path,
complete atomic Note content, and overlay/base expected hash (`null` only for create). A script may
validate this choice but must not make the semantic ownership decision.

## Corrections

A correction names an exact affected `sourceId` + `wikiId`. Resolve it with
`obsidian_wiki_read_notes_by_wiki_ids` using a one-element `wikiIds` list, and require the returned
Source identity to match. Zero matches, duplicates, Source mismatch, or unresolved final evidence
is `defer`. Never choose the nearest title/path or create a Note to make an unknown correction
identity succeed. An accepted correction is an `update` of that exact identity.

## ADR Execution Projections

The project ADR remains authoritative. Reread the exact project-relative ADR and verify its content
hash. Queue only future executable hard constraints, never Context, Options, rationale, Status, or
Consequences.

If none remain, skip with:

`Authoritative ADR has no durable execution constraint; no projection created.`

ADR projections are always project-owned. Never neutralize this candidate into a Shared Source.
Preserve `adr_source_id`, `adr_source_path`, and `adr_source_content_hash`; update the sole matching
projection or create only when none exists. Duplicate authority identity is `defer`/broken, not a
targeting choice.

## Skill Cards

Queue a Skill Card only when the staged project pack identity is available and final evidence proves
the workflow is durable. Preserve `skill_name`, semantic version, contract hash, roles, triggers,
and guide type. Same-name identity is unique across bound Sources. Different triggers, task routing,
or lifecycle require a separate pack/Card decision rather than an overloaded Note.

## Shared Neutrality

Select Shared only for genuinely cross-project contracts. Remove project-specific identifiers
without weakening triggers, failure modes, validation, or examples. Blocked terms/patterns and
`deny`/`refuse` are hard stops. Ambiguous ownership is `defer`; never broaden the target to make
staging pass.

## Semantic Consolidation

Multiple candidate IDs may share one queue decision only when final evidence proves they express one
atomic final claim. Preserve all contributing IDs/digests. Exact duplicates and sequential updates
are folded mechanically later; contradictory or independently triggered contracts stay separate.
