
## Interface

`Capture` is the default mode and accepts one `<feature-slug>`. It dispatches one `wiki-capture`
role, waits for that exact child, and reports only queued/skipped/needs-decision counts. It never
shows Note bodies or applies changes to the formal Wiki base.

Optional user modes are:

- `status`: current-project counts only, grouped by repository and feature.
- `review`: current consolidated queued scope and full Markdown diffs; no publication.
- `publish`: no feature slug. Build the same consolidated review, obtain one exact digest-bound
  confirmation, then create one allowlisted draft PR per affected Wiki repository.

Before either `review` or `publish`, dispatch one isolated `wiki-outbox-consolidation` role. It
privately merges only proven semantically equivalent drafts,
defers contradictory or ambiguous drafts for a user decision, and leaves independent contracts
separate. It never publishes or modifies formal base.

Normal users need only understand `queued`, `pr-open`, and `active`. Candidate receipts, hidden Git
refs, object commits, locks, and recovery manifests are diagnostic implementation state.

## Capture transaction

1. Require one canonical feature slug. If grill `CONTEXT.md` or `docs/adr/` changed, first run the
   existing interruption-safe bridge so those increments enter the same feature journal:

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/grill_context_to_candidates.py <repo-root> --feature-slug <feature-slug> --since <branch-point>
```

2. Resolve the trusted metadata-only descriptor for `grill-adapter:wiki-capture` before dispatch:

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/child_role_loader.py resolve \
  --plugin-root ${CLAUDE_PLUGIN_ROOT} \
  --role grill-adapter:wiki-capture
```

   The coordinator must not read, echo, or inline the Capture role body. Supply the exact feature
   slug, bounded limits (`candidateLimit <= 200`, `noteReadLimit <= 24`,
   `evidenceReadLimit <= 32`), explicit final evidence refs, and these plugin references:
   `${CLAUDE_PLUGIN_ROOT}/skills/update-wiki/references/targeting.md` and
   `${CLAUDE_PLUGIN_ROOT}/skills/update-wiki/references/content-templates.md`.
3. Spawn exactly one Capture agent. Do not analyze candidates inline, dispatch per candidate, or
   spawn a replacement on timeout/failure.
4. The returned agent path is a handle, not a result. The wait is the only legal next operation after dispatch.
   Do not send a user message, ask a question, call MCP, run a command, or continue
   the host workflow first. Wait for that same agent path until terminal. Timeouts, queued/running
   status, transport interruptions, and capacity delays require another bounded wait on the same
   handle. Accept terminal output only when its author is that exact child.
5. Validate the terminal JSON envelope. Return only `planId`, queued/skipped/needs-decision counts,
   and at most three controlled caveats. Dispatch, transport, capacity, lifecycle, malformed-output,
   or staging failure is `broken`; never report it as zero candidates or successful Capture.

### Codex dispatch transaction

Use `collaboration.spawn_agent` with `fork_turns: "none"`; its `message` contains the exact resolved
`roleDescriptor` and bounded Capture input above, never a role body, excerpt, transcript, or other
operation's input. The bootstrap instruction requires the child to run:

```bash
python3 <derived-plugin-root>/scripts/child_role_loader.py load \
  --role grill-adapter:wiki-capture \
  --source <roleDescriptor.source> \
  --expected-digest <roleDescriptor.expectedDigest>
```

before any Wiki call. The child derives its plugin root only from `roleDescriptor.source`. Descriptor
resolution, source containment, digest mismatch, content drift, unreadable role, or loader failure
is `broken` with `role-load-failed`; do not fall back to an inline Capture. After spawn returns a
path, use the separate `collaboration.wait_agent` operation. That wait does not accept a target, so
verify the terminal message author against the saved path. Use bounded waits of up to `300000`
milliseconds and repeat on non-terminal status. Never call the generic `functions.wait`, never send
commentary between spawn and terminal, and never spawn a second child.

Claude Code invokes the registered `grill-adapter:wiki-capture` role directly with the same complete
input and exact-handle wait discipline. Runtime mechanics differ; role, permissions, plan, staging,
and compact output contracts do not.

## Batch consolidation

For `review` and `publish`, resolve the trusted descriptor for
`grill-adapter:wiki-outbox-consolidation` and dispatch exactly one child with only
`changeLimit: 200`. The coordinator must not read, echo, or inline this role, and the child must
load the descriptor's exact source/digest through `child_role_loader.py load` before any Wiki call.
Use the same Codex `fork_turns: "none"`, exact-handle, wait-only-next-operation, repeated bounded
wait, author verification, and `broken` failure discipline as Capture. Claude Code invokes the
registered Outbox role directly. Do not inspect Outbox bodies or perform semantic grouping inline.

The child may call only current-project Outbox review/draft-view/correction tools. It appends merge
successors for proven equivalents and deferred successors for contradictions or ambiguity; it does
not exclude, delete, publish, or choose truth. A `partial` or `broken` result stops publication and
requires user review. Accept `ok` only when the returned digest exactly matches the immediately
following deterministic `outbox review` result.

## Review

Run:

```bash
node ${CLAUDE_PLUGIN_ROOT}/mcp/obsidian-wiki/dist/index.js outbox review
```

Show the returned consolidated per-repository Markdown diffs and plan digest. Sequential changes to
one Note appear once with all contributing entry/feature provenance. The review is local,
non-authoritative, and never makes queued or open-PR content available to formal research.

At the user's request, translate review corrections into one immutable successor at a time with:

```bash
printf '%s\n' '<correction-json>' \
  | node ${CLAUDE_PLUGIN_ROOT}/mcp/obsidian-wiki/dist/index.js outbox correct
```

Supported actions are `exclude`, `defer`, `delete`, `revise`, and `merge`. Resolve each correctable
`entryId` only from the current review; `entryIds` is provenance, not the correction target list.
`revise` supplies one complete reviewed Note; `merge` supplies all current source
entry IDs, an included target entry ID, and one complete reviewed Note. Never edit or delete prior
entries. Every correction invalidates the prior digest, so rerun batch consolidation and review.

## Publish

Enter only when the user explicitly asks to publish. Do not require or accept a feature slug.

1. Run the isolated batch consolidation transaction, then `outbox review` immediately before
   confirmation. Show the exact repository/path scope, full
   diffs, confirmation-required changes, and immutable `planDigest`.
2. Obtain explicit confirmation for that exact digest and the resulting commits, pushes, and draft
   PRs. Note queueing does not authorize Git publication. Any new entry, edit, exclusion, policy
   change, binding change, or base drift invalidates the confirmation and requires a fresh review.
3. After confirmation only, run:

```bash
printf '%s\n' '{"planDigest":"sha256:<confirmed-digest>","confirmed":true}' \
  | node ${CLAUDE_PLUGIN_ROOT}/mcp/obsidian-wiki/dist/index.js outbox publish
```

4. Report repository, branch, commit, draft PR URL, and any mechanically deferred conflicts. A
   same-path or identity conflict remains as a deferred immutable successor while unrelated paths
   and repositories continue. Never merge, approve, force-push, reset,
   stash, clean, or delete branches. Open PR content remains unavailable to formal research until a
   human merges it and the configured base worktree synchronizes.
5. On interruption, rerun the same confirmed request. The Outbox run resumes from immutable object,
   commit, remote branch, or PR state without duplicating publication.

## Authority and safety

- Markdown on merged synchronized Wiki base remains the sole durable Wiki truth.
- Outbox metadata, Git objects, reports, receipts, and manifests are machine-local derived state.
- Formal Disclose/Carry/Bind always read clean merged base and never the Capture draft view.
- Only the Capture role may use base plus the current project's Outbox overlay for targeting;
  isolated Outbox consolidation may read queued drafts solely for batch semantic review.
- Source binding, `deny`/`refuse`, confirmation, Shared neutrality, atomic Note schema, stable
  `wiki_id`, ADR/Skill Card identity, typed links, CAS, and path allowlists remain fail-closed.
- The Capture agent performs semantic durable/atomic/ownership/neutrality judgment but cannot write
  Notes, Git, journals, Outbox internals, or publication state. The deterministic staging interface
  owns identity, hashing, schema, policy, locking, Git objects, refs, and atomic persistence.
- For an ADR candidate with no future executable obligation, record the exact skip reason:
  `Authoritative ADR has no durable execution constraint; no projection created.`
  Never neutralize this candidate into a Shared Source; ADR execution projections remain project-only.

## Legacy recovery

Legacy `kept + applied` receipts and feature-scoped `wiki-publish.json` runs remain recoverable by
the bundled legacy publisher while migration is pending. Do not start a new direct Note apply flow.
If legacy state is detected, migrate or finish that exact retained transaction before new Capture;
never delete receipts/manifests or manually recreate branches. The legacy command remains:

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/wiki_candidate_journal.py fold \
  --journal .grill-adapter/context/<feature-slug>/wiki-candidates.jsonl \
  --feature-slug <feature-slug> \
| node ${CLAUDE_PLUGIN_ROOT}/mcp/obsidian-wiki/dist/index.js publish
```

This compatibility path is diagnostic recovery, not the normal user interface.
