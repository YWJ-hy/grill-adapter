## grill-adapter conventions (plain Claude Code host)

Generated by grill-adapter. This block wires the grill-adapter plugin's skills, hooks, and engine into a plain Claude Code workflow **by convention only — no host skill is patched**. Every touchpoint below is reached by invoking a skill; the skills own their own script paths, so nothing here hard-codes an install location. There is no fixed planning framework here, so you invoke each touchpoint yourself at the matching moment.

### Candidate journal — throughout the workflow

When discovery (or `grill-with-docs`), specification, tickets, implementation, review, or debugging surfaces a possible durable Wiki Note, Skill Card registration, or evidence-backed correction to a known bound Note, run `/grill-adapter:candidate-journal append <feature-slug> <stage>`. A correction records the affected `sourceId` + stable `wikiId`, correction claim, evidence refs, and observed impact. Every stage targets the same `.grill-adapter/context/<feature-slug>/wiki-candidates.jsonl` append-only journal; do not write Obsidian or hand-edit the JSONL. `/grill-adapter:update-wiki` remains the only semantic keep-or-skip gate.

### Disclose — before proposing an approach

Run `/grill-adapter:wiki-research` (phase `brainstorm`) to surface relevant project/shared wiki as lightweight context. On Codex, dispatch is a handle: immediately wait on that same researcher path before any user-facing response, question, MCP call, or next workflow step, repeating bounded waits until terminal. Dispatch/capacity/lifecycle failure is a caveat or `broken`, never `no-relevant`. If none applies, record a one-line N/A and continue. Write no sidecar here.

### Verify — while drafting a spec/plan

Run `/grill-adapter:source-truth-check` to render the source-of-truth policy (`spec-pre` for a spec, `plan-pre` / `plan-review` for a plan) and honor any block: do not edit `truth/edit: never` paths; require explicit authorization for `truth/edit: ask` paths.

### Carry — when writing an implementation plan

Sidecars anchor on the feature, not on a plan file: they live in `.grill-adapter/context/<feature-slug>/`, and a ticket roster — not a plan's headings — carries the task identities.

1. Run `/grill-adapter:wiki-research` (phase `plan`), then follow it to scaffold the schema-v6 `.grill-adapter/context/<feature-slug>/wiki-context.json` from its bound Obsidian Note/Skill Card selection (`wiki_context_render.py --scaffold … --feature-slug <feature-slug> --ticket-source manual`) and edit each Note/Card's `destination` once. Expired Notes are excluded; review-due Notes remain eligible with warnings, and Carry/freeze/Bind recompute freshness. The sidecar must not contain Note bodies.
2. Once the tasks are settled, write the ticket roster `.grill-adapter/context/<feature-slug>/ticket-roster.json` (`/grill-adapter:wiki-research` carries the roster shape). There is no fixed tracker here, so use whatever the user points you at — a task list, issues, a plan document's sections. `taskId` is any stable id; `text` is that task's full text verbatim, since it is the fingerprint input.
3. Run `--finalize` once with `--ticket-roster`, mark selected but unrelated candidates `not-applicable` so they stay out of execution, route each applicable Note/Card to roster task IDs, and preserve every Card's name/version/contract hash/triggers/roles/discovery state.
4. After the user approves the routed constraints, run `/grill-adapter:wiki-readiness` freeze once with `--all` for the roster. It creates each task's `<taskId>.wiki-implement.md` and `<taskId>.wiki-review.md` from the same approved snapshot.

The sidecar is the record of which wiki constrains this feature. Nothing under `.grill-adapter/context/` is committed — sidecar, roster, and candidates are local working state that execution reads in place. Never `git add -f` them.

### Cross-session continuation

`wiki-readiness` and candidate-journal writes refresh a feature-local `wiki-session-state.json` best-effort. On SessionStart, the hook may show its last explicitly selected task, artifact digests, readiness status, candidate count, and next command. Treat it only as a navigation hint: it does not establish that the current prompt is for that ticket and it never supplies Wiki constraints. Resume through `/grill-adapter:wiki-readiness <task-id>`, which remains the authority and revalidates the current roster/context/snapshots.

### Wiki readiness + Bind — before implementing each task

For every task, invoke `/grill-adapter:wiki-readiness` before the first code edit. It establishes one stable task identity: reuse a formal finalized context when present, create one full-body task for a direct tracker issue, or create one `manual` task from the confirmed conversational brief without silently splitting it.

The skill performs late formal selection and Carry only when no formal context matches. `no-relevant` and `disabled` continue without Wiki context. A configured but invalid research/Carry/Bind path is `broken`: explain it and let the user stop or continue without Wiki context. On continue, partial or stale output must not be read, injected, or executed. ADR-backed projections additionally revalidate their project-relative authority path and content identity in Carry/Bind; missing, escaping, malformed, or changed ADRs use the same `broken` choice. Wiki validation stays fail-closed while host implementation availability stays fail-open.

For `ready`, `wiki-readiness` internally runs `/grill-adapter:wiki-materialize <task-id>` with role `implementer` and consumes the frozen `<task-id>.wiki-implement.md` task contract. Do not invoke a second materialization just because the SessionStart hook noticed a pending snapshot. The matching `<task-id>.wiki-review.md` is frozen at the same approval point for later review. The schema-v2 files contain only the routed Notes, role-required Skill Cards, and bounded de-duplicated 1-hop `depends_on` closure for their roles; required `freshnessEntries`, embedded metadata, and the receipt digest protect freshness, task fingerprint, and body. Legacy schema-v1 snapshots must be re-frozen. The `source-truth-lint` hook lints real changed files; resolve any `block`/`ask` before completing the task.

While implementing, invoke `/grill-adapter:candidate-journal` with stage `implementation` for durable decisions/gotchas and keep going.

### Reviewer Bind — before review subagents

At review entry, identify the exact current task and reuse its implementation readiness receipt through `/grill-adapter:wiki-readiness`. Run its `review-handoff` command **before spawning** any isolated Standards and Spec review subagents. Do not perform late research, repair Carry, or require Wiki health before review.

A valid `ready` receipt validates only the current task's approved `<task-id>.wiki-review.md`, re-evaluates direct and one-hop Note freshness, and derives `<task-id>.wiki-review-handoff.md` without overwriting the snapshot. Give both axes the **same read-only handoff Markdown file** and require each to read it; the actual reviewer invokes every verified project skill required by a Card. Standards and Spec retain their separate responsibilities and output structure.

`no-relevant`, `disabled`, `broken`, `unknown`, and any receipt/context/snapshot failure, including ADR authority drift, are a non-blocking caveat. Continue review without Wiki constraints and never inject stale, partial, or edited output. Independent review with no exact task/receipt uses the same unknown path. After review completes, continue the normal Capture path below.

### Capture — after the work is reviewed/accepted

Run `/grill-adapter:update-wiki` to validate/fold the journal, reconcile unresolved candidates against final review/code/spec evidence, explicitly consolidate related claims, and record keep/skip/defer for each final candidate. If the project keeps grill-style knowledge files (`CONTEXT.md`, `docs/adr/`), the skill first converts that increment into journal events via its own grill bridge (bridge, not `import-wiki`). The `wiki-capture` hook reminds only on pending/deferred work or an invalid journal.

Generated ADR projection candidates keep the project ADR authoritative: retain only durable execution constraints, skip when none exist, target the project Source, and update by `adr_source_id`; never copy rationale/options/consequences or neutralize into Shared Wiki. Ordinary non-ADR decision candidates are unchanged.

For a correction candidate, stable-read the exact affected `wikiId` and require its returned `sourceId` to match. Missing, duplicate, mismatched, or drifted identities stay `deferred`; never create a Note to make an unknown identity succeed. An unresolved correction is only a maintenance signal and never hides or changes the active Note. Accept it only after final evidence, then use an explicit `update` target, structured diff, policy authorization, and matching apply receipt before recording `kept`; otherwise record an explicit `skipped` or `deferred` outcome.

For each ordinary Obsidian Note candidate, require an explicit target decision before proposal: `update` only for a same-theme refinement; `create` a sibling Note with a new stable `wiki_id` for an independent contract with a different trigger, lifecycle, failure mode, validation path, or task-routing need. Same module or code owner is not enough to share a Note. If the split is ambiguous, defer and ask instead of appending to the nearest Note.

For `wiki.provider: obsidian`, Capture must use `obsidian_wiki_propose_note_change`, show its structured diff, then use `obsidian_wiki_apply_note_change` only when policy permits and confirmation was explicit. Never edit the Vault worktree directly; conflicts remain deferred and recoverable. An executable process first goes through `scaffold-practice-skill stage-card`; its name/version/contract-hash candidate is pending and the scaffold never writes an index. A successful apply or open PR is not merged/discoverable knowledge.

Default Capture ends after all outcomes are recorded and reports any `kept+applied` receipts grouped by repository. It does not show a Git publish confirmation or start a draft PR. Only when the user explicitly asks `/grill-adapter:update-wiki publish <feature-slug>` may it show the exact repository/Note publish scope, obtain explicit Git publishing confirmation, and use its bundled resumable publisher to create one allowlisted draft PR per touched repository and coordinate peer PRs. On interruption, rerun the same publish step; never delete its local run manifest or manually recreate branches. Open PR content remains unavailable to formal research until merge, base synchronization, and revalidation.

For Wiki lifecycle maintenance, invoke `/grill-adapter:wiki-maintenance audit <feature-slug>` or `/grill-adapter:wiki-maintenance consolidation <feature-slug>`. Both modes dispatch exactly one read-only maintenance agent and immediately wait on that same path. Audit privately checks freshness, contradiction, and overloaded Notes through bounded `obsidian_wiki_maintenance_summary` and Note reads. Consolidation privately compares a bounded deterministic `obsidian_wiki_consolidation_candidates` replay of unresolved canonical feature candidates, groups only semantically equivalent or contradictory durable claims, and keeps contracts with different triggers, lifecycles, failure modes, validation paths, task routing, Card contracts, or ADR identities separate. The main session receives only a validated schema-v1 report path plus compact summary; candidate claims, evidence, Note bodies, journal prose, and agent reasoning stay private. Reports are metadata-only, proposal-only, non-authoritative, and never replace task identity, readiness, Bind, Capture review, proposal, or authorization. Dispatch/transport/capacity/lifecycle failure, malformed or drifting journals, unhealthy bindings, identity drift, or report validation failure is `broken`; do not analyze inline or reuse a stale report. The role cannot write/apply/publish or modify journal, Git, task context, or host state. Invoke `/grill-adapter:migrate-wiki` separately for its bounded legacy section-repartition pass or confirmed Obsidian Note maintenance/repartition mode; those modes remain proposal-driven and never edit cut-over legacy roots directly.

A maintenance report is non-authoritative, and never replaces task identity, readiness, Bind, proposal, or authorization.
Both maintenance modes use one normalized UTC `asOf` timestamp for the complete invocation.
Audit keeps bounded identity/body-read limits; consolidation keeps one global candidate limit.
The coordinator immediately waits on that same path, and the main session receives only a validated schema-v1 report path plus compact summary. Dispatch/transport/capacity/lifecycle failure is `broken`. The role cannot call write/apply/publish tools.

### Runtime health and adoption

Before the first formal Obsidian selection, and after any binding, registry, repository-base, bridge, or migration change, require the operator to run `obsidian-wiki doctor` and `grill-adapter doctor <project-root>` from the two installed npm packages. `setup-init-obsidian` checks both packages before using them. `obsidian-wiki init` creates the machine-local JSONC configuration, `config set-location` changes its path, and `bridge start` launches the configured loopback writer. `adoptionState: shadow-validation` means the Obsidian path is active while legacy roots remain unchanged for migration evidence; it is not a legacy runtime fallback. Do not cut over until migration verify succeeds and the user separately confirms cutover. `adoptionState: cutover-complete` means only the migration-covered legacy roots are read-only archives.

If Note apply or Git publishing is interrupted, preserve the candidate journal, write receipts, migration manifest, and publish run manifest. Rerun the same publish step or migration operation so it can reconcile recorded identities; never repair recovery by editing the Vault worktree, deleting manifests, or reading legacy content as a fallback.

### Debug

After root-cause evidence narrows the failure, optionally run `/grill-adapter:wiki-research` (phase `debug`, ≤2 sections) for a targeted lookup. After a verified fix, run `/grill-adapter:break-loop` for a retrospective; it hands durable candidates to `/grill-adapter:update-wiki`.

### Boundary

grill-adapter's standalone utility skills are utilities, not workflow steps; running one does not imply any implementation/review is complete or verified.
