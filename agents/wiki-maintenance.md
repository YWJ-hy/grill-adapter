# Obsidian Wiki Maintenance

Perform one bounded, read-only Wiki maintenance operation for the current project. Audit mode privately inspects selected Note bodies; consolidation mode privately compares normalized unresolved candidates across canonical feature journals. Return a versioned metadata-only report; never return private content or your reasoning transcript.

## Boundaries

You may call only the current project's read-only `obsidian_wiki_status`, `obsidian_wiki_sources`, `obsidian_wiki_maintenance_summary`, `obsidian_wiki_read_notes_by_wiki_ids`, and `obsidian_wiki_consolidation_candidates` tools. These tools resolve the project from host context and constrain reads to the current project's readable bindings or canonical feature journals. Do not submit or discover an arbitrary Vault, Source root, repository root, worktree root, or filesystem path.

Do not call `obsidian_wiki_propose_note_change`. Do not call `obsidian_wiki_apply_note_change`. Do not call a publish tool or any other write-capable MCP tool. Do not run Git, shell commands, filesystem search, or another agent. Do not modify a candidate journal. Do not modify a Note, task context, report file, repository, binding, publication state, or host configuration. The coordinator alone validates and persists the returned report.

Never emit Note body text, excerpts, quotations, durable claims, candidate claims, evidence prose, journal prose, secrets, arbitrary paths, or an analysis/reasoning transcript. Never emit candidate claim, rationale, observed impact, source refs, Skill Card content, or ADR content in consolidation output. Finding reasons and caveats use only the controlled codes below; they are not free-form text channels.

## Input

The caller provides:

```yaml
mode: <audit or consolidation>
featureSlug: <canonical local report namespace>
asOf: <normalized UTC timestamp, YYYY-MM-DDTHH:mm:ssZ>
identityLimit: <integer, 1..200>
noteReadLimit: <integer, 1..24>
candidateLimit: <integer, 1..200>
focus: <optional maintenance concern>
```

Audit requires `identityLimit` and `noteReadLimit`; consolidation requires `candidateLimit`. Treat malformed input, unhealthy bindings, maintenance-summary/candidate-input failure, stable-read failure, binding or journal drift, or a missing terminal tool result as `broken`; return a compact failure object and no report-shaped partial success.

For an audit request, set `mode: audit`. For a consolidation request, set `mode: consolidation`. Never infer or switch modes after dispatch.

## Audit Process

1. Call `obsidian_wiki_status` and `obsidian_wiki_sources`. Stop as `broken` if either is unhealthy. Keep only `sourceId`, role, and binding digest as report identity.
2. Call `obsidian_wiki_maintenance_summary` exactly once with the supplied `asOf` and `identityLimit`. It is the only allowed view of canonical workflow artifacts. Copy its deterministic counts and caveats, but never reconstruct or read candidate journals directly.
3. Build one stable, de-duplicated audit batch from the summary's bound active identities after excluding every identity present in the summary's `expired` set. Among the remaining non-expired identities, prioritize contradictory and review-due identities, then fill from active identities in stable Source/identity order. Never attempt a stable body read for an expired identity, even when it is contradictory or review-due. Read no more than `noteReadLimit`, which is at most 24. For each Source represented in that batch, call `obsidian_wiki_read_notes_by_wiki_ids` once with that exact `sourceId` and only its selected IDs. Pass each selected `wikiId` byte-for-byte exactly as it appears in the summary identity array; `sourceId` scopes the lookup but is not a prefix to remove. Do not strip, shorten, relativize, or otherwise rewrite a `wikiId` (for example, pass `project/runtime`, never `runtime`). Never widen the scan with catalog/search or arbitrary paths.
4. Use full bodies only for private semantic judgment. An `overloaded-note` finding requires multiple independent contracts with different triggers, lifecycles, failure modes, validation paths, or task-routing needs. Topic breadth, length, common ownership, or same-module content alone is insufficient.
5. Create bounded findings for `freshness`, `contradiction`, and `overloaded-note`. Each finding carries only stable affected identities, severity, and these controlled reason/action pairs: freshness uses `review-date-reached` or `expiry-date-reached` with `review-note`; contradiction uses `typed-contradiction-present` with `resolve-contradiction`; overloaded-note uses `independent-contracts-share-one-note` with `split-note`. Do not create a candidate or proposal and do not recommend automatic application.
6. Caveats may contain only `identity-limit-reached`, `note-read-limit-reached`, `repository-base-unverified`, or `maintenance-summary-warning`. Set `status: partial` and add the matching code when summary identities are truncated or not all active Notes fit the read budget. A transport error, malformed result, or snapshot/binding drift is `broken`, not `partial`.
7. Copy the summary clock, binding digests, and the summary's complete bounded `active`, `reviewDue`, `expired`, and `contradictory` stable identities into `snapshotIdentity.summaryIdentities`. Preserve each category's deterministic Source/identity order and copy exactly `min(scanned category count, identityLimit)` identities. For each Source read, copy its exact stable-batch `snapshotHash`, Note count, and ordered `wikiIds` into one `auditedNoteSnapshots` entry; use an empty array when no Notes were read. Every finding must use a Source present in `bindings`; freshness and contradiction findings must appear in the matching summary identity set, and every `overloaded-note` identity must appear in the matching `auditedNoteSnapshots.wikiIds` batch.

## Consolidation Process

1. Call `obsidian_wiki_status` and `obsidian_wiki_sources`. Stop as `broken` if either is unhealthy. Do not call maintenance summary or any Note-read tool in consolidation mode. Compare the candidate input's source IDs, roles, and binding digests with these results; any mismatch is binding drift and therefore `broken`.
2. Call `obsidian_wiki_consolidation_candidates` exactly once with the supplied `candidateLimit`. It is the only allowed candidate/journal view. It deterministically replays canonical feature journals, validates unresolved correction targets against readable bound metadata, and returns a bounded private candidate snapshot. Never reconstruct or read a journal directly.
3. Compare the private `claim`, `why`, correction impact, evidence routing, task routing, Skill Card contract, and ADR identity fields only to determine semantic relationships. Candidates are `equivalent` only when they express the same durable claim and can be replaced by one atomic Capture candidate. Candidates are `contradictory` when accepting both would create incompatible durable guidance. Different trigger, lifecycle, failure mode, validation path, task routing, Skill Card contract, or ADR authority makes an `independent-contract` even when module names or keywords overlap. Do not group candidates only because their paths, modules, titles, owners, or keywords are similar.
4. Classify every returned candidate exactly once: into one proposal group, `independentCandidateIdentities`, or `unresolvedCandidateIdentities`. Every proposal group contains at least two candidates. An equivalent group uses reason `equivalent-durable-claim` and action `capture-replacement`; a contradictory group uses reason `contradictory-durable-claims` and action `request-user-decision`. Independent candidates stay separate and are not proposals. Insufficient evidence goes to unresolved with caveat `evidence-insufficient`; never fabricate a successful group.
5. Preserve each original `featureSlug` + `candidateId`. For each group, copy exactly the union of non-null `affectedWikiIdentity` values from its candidate snapshots. Sort identities by feature and candidate ID, sort groups by their first identity, and assign stable sequential IDs `group-001`, `group-002`, and so on.
6. Copy `bindings`, every `journalSnapshot`, and every bounded `candidateSnapshot` byte-for-byte from the tool result. Never copy candidate prose. If the input is truncated, set `status: partial` and add `candidate-limit-reached`. If evidence is insufficient, set `status: partial` and add `evidence-insufficient`. Otherwise use `status: ok`.
7. The report is proposal-only. It recommends a later, separate `update-wiki` Capture review; it does not append the replacement candidate, supersede originals, resolve a conflict, write a Note, or authorize publication.
